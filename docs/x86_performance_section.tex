\subsection{Software Performance on x86 Processors}
We provide two implementations for the x86 platform: a portable ISO~C99 reference implementation (\texttt{ref/}) and an AVX2-optimized implementation (\texttt{avx2\_weaver/}). The optimized build vectorizes polynomial arithmetic and matrix sampling for $n{=}256$ (\textsc{Weaver-512} and \textsc{Weaver-1024}). For \textsc{Weaver-2048} ($n{=}512$, $k{=}4$), it additionally provides an AVX2 NTT in standard coefficient order, SHAKE128$\times$4 parallel matrix generation, vectorized base multiplication, fused \texttt{polyvec\_basemul\_acc}, and AVX2 modular reduction.

\subsubsection{Experimental Setup}
All measurements reported in Tables~\ref{tab:x86_perf}--\ref{tab:overhead_breakdown} were taken on the following platform:
\begin{itemize}
  \item \textbf{Processor:} AMD EPYC 7C13 (x86-64), 2 logical CPUs exposed to the guest; nominal model frequency reported by the firmware: 2.0\,GHz.
  \item \textbf{Operating system:} Linux (Debian-based), kernel \texttt{6.1.0-44-amd64}, 64-bit.
  \item \textbf{Compiler:} GCC~12.2.0 with \texttt{-std=c99 -O3 -march=native -fomit-frame-pointer}.
  \item \textbf{ISA extensions used by the optimized build:} AVX2, BMI2, POPCNT (\texttt{-mavx2 -mbmi2 -mpopcnt}).
  \item \textbf{Optimized build flags:} \texttt{USE\_AVX\_NTT=1}, \texttt{USE\_AVX\_COMPRESS=1}, \texttt{USE\_GETRANDOM=1}; for \textsc{Weaver-2048} additionally \texttt{USE\_AVX\_FQ\_512=1} and \texttt{USE\_AVX\_GEN\_MATRIX512=1}. Link-time optimization (\texttt{-flto}) is enabled except for a small set of translation units where LTO is disabled for correctness (Keccak$\times$4 / rejection sampling / compression).
  \item \textbf{Randomness for benchmarks:} Non-deterministic \texttt{randombytes} calls use the Linux \texttt{getrandom(2)} syscall when \texttt{USE\_GETRANDOM=1}, matching the entropy source used by the pq-crystals Kyber AVX2 reference (\texttt{randombytes.c}). Known-answer tests still seed the in-tree AES-256-CTR-DRBG via \texttt{randombytes\_init} and are unaffected.
  \item \textbf{Cycle counter:} \texttt{RDTSC}-based timing via the project-supplied \texttt{cpucycles} module; reported values are \emph{median} cycle counts per operation, with overhead subtracted once per interval.
  \item \textbf{Benchmark programs:} Weaver AVX2 timings from \texttt{avx2\_weaver/bench/bench\_components.c} ($N_{\mathrm{test}}{=}1{,}000$ per run). ML-KEM timings from pq-crystals Kyber commit \texttt{4768bd3}, \texttt{avx2/test/test\_speed*} ($N_{\mathrm{test}}{=}1{,}000$). Each table entry is the median of five consecutive full benchmark runs on an otherwise idle system.
  \item \textbf{Correctness checks:} Before benchmarking, ICCS KEM known-answer tests, ref/AVX cross-checks, and extended regression tests (\texttt{make test-extended}) were executed for all three Weaver parameter sets.
\end{itemize}
\noindent
\textbf{Note.} The host is a virtualized AMD EPYC system. Absolute cycle counts are platform-dependent; relative comparisons between schemes on the same machine are the intended use of Table~\ref{tab:weaver_vs_mlkem}.

\paragraph{Comparison with ML-KEM.}
At matching $(n,k)$, \textsc{Weaver-512} and \textsc{Weaver-1024} reduce $|\mathsf{pk}|$ and $|\mathsf{ct}|$ (Table~\ref{tab:bandwidth}) but incur higher CPU cost on encapsulation and decapsulation because of algorithmic features absent from ML-KEM: randomized lifting $\mathrm{Inv}_q$ on the public key during encryption, hierarchical BCH message encoding/decoding, and (for \textsc{Weaver-512}) a larger CBD parameter $\eta_1{=}5$ versus $\eta_1{=}3$ in ML-KEM-512.
Profiled on the same AVX2 build, $\mathrm{Inv}_q$ and BCH encode contribute on the order of $3$--$3.5$\,k and $\approx 0.2$\,k cycles per encapsulation at $(256,2)$, while BCH decode adds $\approx 3$\,k cycles to decapsulation; at $(256,4)$, $\mathrm{Inv}_q$ alone is $\approx 10$\,k cycles per encapsulation.

Key generation is dominated by the shared Kyber-style CPA path ($\texttt{gen\_matrix}$, noise sampling, NTT, base multiplication) once entropy is drawn fairly: with \texttt{USE\_GETRANDOM=1}, \texttt{randombytes(64)} drops from $\approx 19$\,k to $\approx 2.6$\,k cycles, and \textsc{Weaver-512} key generation falls from $\approx 2.3\times$ to $\approx 1.3\times$ the ML-KEM-512 cost; \textsc{Weaver-1024} key generation matches ML-KEM-1024 within measurement noise ($\approx 1.0\times$).
Encapsulation remains $1.5$--$1.6\times$ slower than ML-KEM at both $(256,2)$ and $(256,4)$ because every encapsulation and FO re-encryption executes the full Weaver encrypt path including $\mathrm{Inv}_q$ and message encoding.
Decapsulation can be faster than encapsulation for \textsc{Weaver-512} ($30.6$\,k vs.\ $28.7$\,k cycles here) even though FO decapsulation re-runs encryption: the timed \texttt{crypto\_kem\_enc} entry includes an extra \texttt{randombytes} draw for the FO message, which \texttt{crypto\_kem\_dec} omits.

Three categories explain the gap over ML-KEM.
\emph{Design-intrinsic} overhead is dominated by $\mathrm{Inv}_q$ and BCH encoding ($+5{,}800$ cycles at $(256,2)$ and $+13{,}100$ at $(256,4)$), features deliberately added for proof tightness and bandwidth, not for raw speed.
\emph{Parameter-induced} overhead appears mainly on \textsc{Weaver-512}, where $\eta_1{=}5$ versus $\eta_1{=}3$ in ML-KEM-512 adds $+2{,}820$ cycles in centered-binomial sampling; at $(256,4)$ both schemes use $\eta_1{=}2$, so this term collapses to $+160$ cycles (within noise).
\emph{Implementation-aligned} primitives---\texttt{gen\_matrix}, NTT, and base multiplication---differ by at most a few percent, indicating that the vectorized polynomial core is not the bottleneck.

Key generation illustrates the same split.
Because $\mathrm{Inv}_q$ and BCH are not invoked, \textsc{Weaver-1024} key generation matches ML-KEM-1024 ($38{,}600$ vs.\ $38{,}740$ cycles, ${\approx}1.00\times$).
The remaining \textsc{Weaver-512} gap (${\approx}1.30\times$, $+5{,}060$ cycles) comes from $\eta_1{=}5$ noise expansion ($+2{,}820$ cycles for two polynomials) and $9$-bit compressed public-key packing ($+1{,}260$ cycles in \texttt{pack\_pk} versus $12$-bit coefficient storage in ML-KEM), plus a small CCA tail (\texttt{H}($\mathsf{pk}$), copy of~$z$).

Excluding the two design-intrinsic components ($\mathrm{Inv}_q$ and BCH), the remaining encapsulation overhead is at most $5{,}060$ and $7{,}660$ cycles on \textsc{Weaver-512} and \textsc{Weaver-1024}, respectively ($28\%$ and $20\%$ of the corresponding ML-KEM encapsulation medians, or $47\%$ and $37\%$ of the measured Weaver excess).
This confirms that the performance gap is primarily a deliberate bandwidth--security trade-off rather than a gap in core lattice arithmetic.

Component-level timings on the AVX2 build show that \texttt{gen\_matrix} is already within $\approx 5\%$ of ML-KEM's \texttt{gen\_a} at $(256,2)$ ($\approx 5.2$\,k vs.\ $\approx 5.2$\,k cycles); single-polynomial NTT and \texttt{polyvec\_basemul\_acc} differ by at most $\approx 1.6\times$.
The remaining key-generation gap at $(256,2)$ is therefore not matrix generation but CPA-specific work---notably $\eta_1{=}5$ noise expansion ($\approx 7.4$\,k cycles for two polynomials vs.\ $\approx 1.5$\,k for one ML-KEM \texttt{poly\_getnoise\_eta1} call) and compressed public-key packing ($\approx 1.7$\,k cycles).

On \textsc{Weaver-2048}, end-to-end performance is dominated by matrix sampling and serialization; \texttt{gen\_matrix} costs $\approx 47$\,k cycles per call in the AVX2 build, and fused \texttt{polyvec\_basemul\_acc} accounts for $\approx 6$\,k cycles per dot product at $n{=}512$.
