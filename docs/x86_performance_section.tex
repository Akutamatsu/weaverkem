\subsection{Evaluation Methodology and Platforms}
\label{sec:eval-methodology}

To ensure reproducibility and demonstrate the scheme's versatility across
deployment classes, we define the benchmarking environments and metrics as
follows.

\paragraph{Metric definition.}
On x86-64, performance is reported as \textbf{median CPU cycles} measured via
\texttt{RDTSC} with call overhead subtracted
(\texttt{cpucycles\_overhead()}); each entry is the median over five
independent runs of $N_{\mathrm{test}}{=}1{,}000$ timed iterations per run.
On embedded targets, performance is likewise reported as median CPU cycles
(median of $N_{\mathrm{test}}{=}10{,}000$ runs); we additionally report
maximum stack usage to assess suitability for memory-constrained devices.

\begin{itemize}
  \item \textbf{High-performance platform (x86\_64).}
        Single-socket KVM/QEMU guest reporting an \textbf{AMD EPYC 9655P}
        (96-core class, firmware clock \textbf{2.0\,GHz}, 2~vCPUs, 128\,KiB
        L1d/i per core, 1\,MiB L2 per core); host ISA features include AVX2,
        BMI2, POPCNT, and AVX-512.
        \begin{itemize}
          \item \textit{OS:} Linux \textbf{6.1.0-49-amd64} (Debian~12)
          \item \textit{Compiler:} GCC \textbf{12.2.0}
          \item \textit{Flags:} \texttt{-std=c99 -O3 -fomit-frame-pointer
                -march=native -mtune=native -mavx2 -mbmi2 -mpopcnt -flto}
          \item \textit{RNG (benchmark path):} Linux \texttt{getrandom(2)}
                (\texttt{USE\_GETRANDOM=1}), matching the ML-KEM reference;
                KAT paths retain the in-tree AES-256-CTR-DRBG.
        \end{itemize}
        All tables in \S\ref{sec:x86-perf} were collected on this platform.

  \item \textbf{Embedded platform (32-bit ARM).}
        STM32F407 Discovery Board (ARM Cortex-M4) @ 168\,MHz, 192\,KiB SRAM,
        1\,MiB Flash.
        \begin{itemize}
          \item \textit{Compiler:} \texttt{arm-none-eabi-gcc 14.3.rel1}
          \item \textit{Flags:} \texttt{-O3 -mthumb -mcpu=cortex-m4
                -mfloat-abi=hard -mfpu=fpv4-sp-d16}
        \end{itemize}

  \item \textbf{Embedded platform (32-bit RISC-V).}
        CM32M433R\_START Board (RV32IMACF) @ 144\,MHz, 144\,KiB SRAM,
        512\,KiB Flash.
        \begin{itemize}
          \item \textit{Compiler:} \texttt{riscv64-unknown-elf-gcc 14.2.1}
          \item \textit{Flags:} \texttt{-O3 -march=rv32imafc -mabi=ilp32f}
        \end{itemize}
\end{itemize}

\subsection{Software Performance on x86 Processors}
\label{sec:x86-perf}

Unless stated otherwise, the numbers below use the x86\_64 platform and cycle
methodology from \S\ref{sec:eval-methodology}.
We provide two ISO~C99 reference builds and one AVX2-optimized tree:
\begin{itemize}
  \item \textbf{NGCC configuration} (\texttt{Implementations/Reference\_Implementation/}):
        the ICCS submission path uses the SM3-family auxiliary functions in
        \texttt{auxfunc.c} (\texttt{sm3hash}, \texttt{pseudohash}, \texttt{pseudoXOF})
        wired through \texttt{symmetric.h}; matrix expansion uses the corresponding
        pseudo-XOF block size (168~B for \textsc{WEAVER-640}, 136~B otherwise).
        This configuration is used for NIST-style KAT generation and specification
        conformance.
  \item \textbf{Keccak reference configuration} (\texttt{ref/}): a portable Keccak/FIPS~202
        implementation (\texttt{symmetric-shake.c}) with SHA3-512 hashing (modes~3/5),
        SHAKE256 PRFs, and \textbf{SHAKE128} matrix XOFs at all security levels (matching
        ML-KEM's matrix-expansion primitive).
  \item \textbf{AVX2 implementation} (\texttt{avx2\_weaver/}): same Keccak symmetric layer
        as \texttt{ref/}; matrix expansion uses SHAKE128$\times$4 on all modes.
        AVX2 centered binomial sampling (\texttt{USE\_AVX\_CBD=1}) vectorizes
        $\eta\in\{2,3,7\}$ (Kyber-style paths for $\eta{=}2/3$; SWAR popcount for
        $\eta{=}7$); $\eta{=}9$ (\textsc{WEAVER-2048}) remains scalar-equivalent until a
        correct 18-bit cross-byte extract is in place.
        All performance numbers below are measured on this tree so that comparisons with
        ML-KEM (also Keccak-based, SHAKE128 matrix) isolate algorithmic differences rather
        than hash/XOF choice.
\end{itemize}

The AVX2 build vectorizes polynomial arithmetic, parallel matrix sampling, and
CBD at $\eta\le 7$.
For \textsc{WEAVER-640} ($(n,k,q){=}(128,5,3329)$) it enables an AVX2 NTT at
$n{=}128$, SHAKE128$\times$4 matrix generation, and fused 9-bit public-key
compression.
For \textsc{WEAVER-1024} ($(256,4,7681)$) and \textsc{WEAVER-2048}
($(512,4,7681)$) it adds a dedicated $q{=}7681$ AVX2 NTT, SHAKE128$\times$4
matrix generation, fused \texttt{polyvec\_basemul\_acc}, and AVX2 modular
reduction in standard coefficient order.
ML-KEM baselines are from pq-crystals/kyber commit \texttt{4768bd3} (reference
and AVX2 trees), collected on the same x86 platform with the same methodology.
Portable \texttt{ref/} medians disable all \texttt{USE\_AVX\_*} switches; they
use the same Keccak/SHAKE128 symmetric layer as the AVX2 tree so that
reference-vs-reference comparisons with ML-KEM isolate lattice work rather than
hash/XOF choice (the NGCC submission path uses SM3 via \texttt{auxfunc} and is
not included in these tables).

\subsubsection{Comparison with ML-KEM (reference and optimized)}

Tables~\ref{tab:kem_fourway}--\ref{tab:symmetric_strip} compare Weaver against
ML-KEM at both security tiers and both implementation classes.
All rows use the Keccak/SHAKE128 symmetric layer on the Weaver side and the
standard pq-crystals Kyber reference/AVX2 trees on the ML-KEM side
(commit \texttt{4768bd3}, same x86 platform and RDTSC methodology as
\S\ref{sec:eval-methodology}).
Because \textsc{WEAVER-640} uses $(n,k){=}(128,5)$ rather than ML-KEM-512's
$(256,2)$, the 128-bit block is indicative; the 256-bit block matches
$(n,k){=}(256,4)$ and is the fairest end-to-end comparison.

\paragraph{How to read the comparison (recommended narrative).}
We report ML-KEM numbers for context, not as a like-for-like drop-in replacement:
Weaver targets smaller on-the-wire objects via tighter compression, $\mathrm{Inv}_q$
randomized lifting, and BCH coding (Table~\ref{tab:bandwidth}), and uses
parameter sets $(q,\eta_1)$ that differ from Kyber's $(3329,2)$.
Readers should interpret the data in three layers, from most to least apples-to-apples:
\textbf{(i)~Portable reference parity.} On C99/Keccak builds at matched $(n,k){=}(256,4)$,
full encapsulation differs by only \textbf{1.2$\times$}, and \emph{after removing one
matrix-XOF call} the stripped medians agree within \textbf{2\%}
(Table~\ref{tab:symmetric_strip})---the lattice-side budget is essentially the same
before SIMD specialization.
\textbf{(ii)~Where AVX2 diverges.} The end-to-end AVX2 gap (\textbf{4.1$\times$} on
encaps at 256-bit) is not dominated by symmetric primitives once both sides vectorize
\texttt{gen\_matrix}/\texttt{gen\_a}; it reflects \emph{parameter and design choices}
($q{=}7681$ NTT, $\eta_1{=}7$ CBD/PRF, 9--11-bit compress, $\mathrm{Inv}_q$/BCH),
as quantified in Table~\ref{tab:overhead_breakdown}.
\textbf{(iii)~Bandwidth return.} At the 256-bit tier, \textsc{WEAVER-1024} trades
$\approx{}4\times$ higher AVX2 encapsulation latency for \textbf{9\%} smaller total
$|\mathsf{pk}|{+}|\mathsf{ct}|$ (2{,}848 vs.\ 3{,}136~B); \textsc{WEAVER-640} matches
ML-KEM-512 on total wire size (1{,}568~B) while using a higher module rank ($k{=}5$).
We do not claim CPU parity with pq-crystals' mature $q{=}3329$ AVX2 assembly; we claim
that the \emph{reference} lattice work is competitive and that the AVX2 gap decomposes
into identifiable, specification-driven terms rather than a generic implementation deficit.

\paragraph{End-to-end gap.}
At 256-bit security, full encapsulation on the AVX2 build is
\textbf{4.1$\times$} slower than ML-KEM-1024
($99{,}241$ vs.\ $24{,}387$ cycles), while the portable reference implementations
differ by only \textbf{1.2$\times$}
($185{,}977$ vs.\ $150{,}591$).
The AVX2 slowdown is therefore \emph{not} explained by Keccak/XOF cost alone:
ML-KEM's reference code vectorizes NTT, compression, and rejection sampling far
more aggressively than Weaver's portable \texttt{ref/} path, whereas Weaver's
AVX2 tree already closes much of that SIMD gap on matrix expansion
(\texttt{gen\_matrix} within \textbf{1.2--1.5$\times$} of ML-KEM's \texttt{gen\_a}
at $(256,4)$).

\paragraph{Where the cycles go: symmetric vs.\ lattice.}
We attribute \textbf{symmetric-primitive overhead} to (i)~matrix expansion
(\texttt{gen\_matrix} / \texttt{gen\_a}), and (ii)~FO/CCA hashing and
SHAKE256/PRF calls (\texttt{hash\_h}, \texttt{hash\_g}/\texttt{shake256},
\texttt{prf}, \texttt{rkprf})---the same class of work that dominates portable
ML-KEM and Weaver reference builds.
Table~\ref{tab:symmetric_strip} reports encapsulation after subtracting one
matrix-expansion call (the \texttt{gen\_matrix}$^T$ / \texttt{gen\_a} term
present in every encaps path), with \textbf{portable Ref rows first} and
\textbf{AVX2 rows second} at each security tier.
On \textbf{reference} code at matched $(n,k){=}(256,4)$, the stripped medians
are $117{,}208$ cycles (Weaver) vs.\ $114{,}816$ (ML-KEM), i.e.\ within
\textbf{2\%}---essentially the same lattice-side budget once XOF matrix sampling
is removed; at the \textbf{128-bit indicative} tier (different $(n,k)$), stripped
Ref encapsulation is $50{,}856$ vs.\ $56{,}212$ cycles ($0.91\times$).
On \textbf{AVX2}, the same stripping exercise yields $5.3\times$ at
$(256,4)$ ($87{,}022$ vs.\ $16{,}328$) and $3.6\times$ at the 128-bit tier
($34{,}606$ vs.\ $9{,}565$): matrix expansion is no longer the dominant term,
and the residual gap is driven by parameterization ($q{=}7681$ NTT, $\eta{=}7$
CBD/PRF at mode~3) and Weaver-only $\mathrm{Inv}_q$/BCH work, not by Keccak
absorption in \texttt{gen\_matrix}.

\paragraph{Reference vs.\ optimized speedups.}
Table~\ref{tab:avx_speedup_both} shows that ML-KEM enjoys larger AVX2 speedups
(\textbf{5.6--7.0$\times$} on decaps) than Weaver
(\textbf{1.9--2.2$\times$}) on the same platform.
The asymmetry is expected: Kyber's AVX2 NTT at $q{=}3329$ drops a single-polynomial
transform to $\approx{}100$ cycles, while Weaver's $q{=}7681$ AVX2 NTT remains
$\approx{}1{,}800$ cycles; ML-KEM also vectorizes 4-bit/10-bit compression and
$\eta{=}2$ CBD to near-constant cost, whereas Weaver pays for 9--11-bit packing
and $\eta{=}7$ noise at mode~3.
In exchange, \textsc{WEAVER-1024} reduces $|\mathsf{pk}|$ by 16\% and total
wire size by 9\% (Table~\ref{tab:bandwidth}); \textsc{WEAVER-640} matches
ML-KEM-512 on total on-the-wire bytes (1{,}568~B).

\subsubsection{Overhead Decomposition}

Table~\ref{tab:overhead_breakdown} refines the AVX2 encapsulation gap beyond
Table~\ref{tab:symmetric_strip}: component medians from the AVX2
Keccak/SHAKE128-matrix build (\texttt{bin/profile\_encap\_*}) with ML-KEM rows
from the Kyber AVX2 harness.
%
\emph{Design-intrinsic} components---randomized lifting $\mathrm{Inv}_q$ and BCH
message encoding (\texttt{poly\_frommsg})---are absent from ML-KEM; together
they account for $+5{,}430$ cycles at $(128,5)$ and $+5{,}480$ cycles at
$(256,4)$;
i.e.\ about 15\% and 7\% of the respective AVX2 encapsulation gaps vs.\ ML-KEM.
%
\emph{Parameter-induced} overhead is dominated on \textsc{WEAVER-1024} by
$\eta{=}7$ centered binomial sampling and by the $q{=}7681$ NTT.
Each \texttt{poly\_getnoise} call is \texttt{prf}$+$CBD; at $(256,4)$ encaps
draws $k{=}4$ noise polynomials, so Table~\ref{tab:overhead_breakdown} reports
the \textbf{sum over four polys} ($21{,}241$ cycles on Weaver vs.\ $1{,}970$ on
ML-KEM in the Kyber harness segment---\textbf{not} a per-polynomial ratio).
Microbenchmarks on the same platform give $\approx{}3{,}350$ cycles per
$\eta{=}7$ draw ($\approx{}3{,}000$ SHAKE256 PRF for 448~B output $+$
$\approx{}350$ CBD) vs.\ $\approx{}987$ cycles per ML-KEM-1024 $\eta{=}2$ draw
($\approx{}850$ PRF for 128~B $+$ negligible CBD); i.e.\ \textbf{$\approx{}3.4\times$
per poly}, explained primarily by $7/2$ times more PRF output bytes rather than
a missing AVX2 CBD kernel.
The $q{=}7681$ NTT adds $\approx{}1{,}700$ cycles per polynomial on the AVX2
Route-A path vs.\ $\approx{}100$ cycles for ML-KEM's $q{=}3329$ assembly NTT.
At $(128,5)$, ML-KEM-512 and \textsc{WEAVER-640} both use $\eta_2{=}2$ in
encaps; the smaller CBD delta ($+1{,}873$) is driven mainly by module rank
($k{=}5$ vs.\ $k{=}2$), not by a larger $\eta$.
%
\emph{Symmetric-primitive} \texttt{gen\_matrix} plus FO hashing/PRFs contribute
only $\approx{}2{,}000$ cycles of the $(256,4)$ AVX2 gap
(Table~\ref{tab:overhead_breakdown}); the reference implementations differ mainly
because scalar \texttt{gen\_matrix} costs $\approx{}69$\,k cycles per call
vs.\ $\approx{}36$\,k for ML-KEM's scalar \texttt{gen\_a} at the same $(n,k)$.
After AVX2 optimization, \texttt{gen\_matrix} is within \textbf{1.5$\times$} of
\texttt{gen\_a} ($\approx{}12.2$\,k vs.\ $\approx{}8.1$\,k cycles at $(256,4)$);
at $(128,5)$ the higher module rank still drives a $\approx{}12.8$\,k vs.\
$\approx{}2.0$\,k cycle gap.

The same split explains key generation: $\mathrm{Inv}_q$ and BCH are not
invoked, yet \textsc{WEAVER-1024} key generation exceeds ML-KEM-1024 by
$\approx{}62{,}000$ cycles because of four $q{=}7681$ NTTs during public-key
packing/unpacking and four \texttt{gen\_matrix} calls per keypair.
On \textsc{WEAVER-640}, 9-bit compressed public-key packing
($\approx{}1{,}600$ cycles per \texttt{polyvec\_compress\_pk}) and five
secret/noise polynomials account for most of the remaining KeyGen gap.
Note that \texttt{kem\_decaps} is faster than \texttt{kem\_encaps} on
\textsc{WEAVER-1024} and \textsc{WEAVER-2048} because the FO re-encryption
inside decapsulation omits the \texttt{randombytes} draw present in
\texttt{kem\_encaps}.

\paragraph{Implementation headroom (AVX2, KAT-safe).}
The AVX2 speedup ceiling is lower than ML-KEM's because several dominant terms
($q{=}7681$ NTT, $\eta{=}7$ PRF) are already partially optimized but cannot be
replaced by alternate NTT conventions without breaking KAT match to the reference
implementation.
Documented headroom on the current parameter sets includes: enabling the existing
$q{=}7681$ assembly NTT ($\approx{}20\%$ on \texttt{poly\_ntt}), invNTT tail
SIMD, and batched SHAKE256$\times$4 PRF for the $k$ encaps noise polynomials
(the latter targets the $\approx{}90\%$ PRF fraction of $\eta{=}7$ \texttt{poly\_getnoise}).
These are incremental gains (order \textbf{10\%} end-to-end on encaps), not a path to
ML-KEM-class $6\times$ ref-to-AVX ratios while $(q,\eta_1)$ remain unchanged.

Excluding the two design-intrinsic components ($\mathrm{Inv}_q$ and BCH), the
remaining AVX2 encapsulation overhead is $+30{,}177$ and $+69{,}374$ cycles on
\textsc{WEAVER-640} (128-bit row) and \textsc{WEAVER-1024} (256-bit row),
respectively.
On the matched $(256,4)$ row this corresponds to $93\%$ of the measured excess;
CBD, $q{=}7681$ NTT, and compression dominate, while $\mathrm{Inv}_q$
and BCH together contribute under 7\%.
Symmetric matrix expansion and FO hashing jointly account for under 3\% of the
AVX2 gap at $(256,4)$, whereas on portable C they explain most of the
1.2$\times$ full-encapsulation ratio (Table~\ref{tab:symmetric_strip}).
The performance gap on optimized builds is therefore a combination of deliberate
bandwidth--security trade-offs \emph{and} the heavier $q{=}7681$ / $\eta_1{=}7$
parameterization, not a shortfall in \texttt{polyvec\_basemul\_acc} (which matches
ML-KEM-1024 at $\approx{}155$ cycles on both sides).

Component-level timings on the AVX2 Keccak build show that
\texttt{gen\_matrix} at $(256,4)$ is $\approx{}1.5\times$ ML-KEM's
\texttt{gen\_a} ($\approx{}12.2$\,k vs.\ $\approx{}8.1$\,k cycles); Keccak
$\times$4 absorption still accounts for the majority of that kernel, but it is
no longer the dominant term in the end-to-end gap once both sides use AVX2.
Single-polynomial NTT at $q{=}7681$ costs $\approx{}1{,}800$ cycles vs.\
$\approx{}100$ cycles for ML-KEM's $q{=}3329$ AVX2 NTT.
The \textsc{WEAVER-640} KeyGen gap vs.\ ML-KEM-512 is driven primarily by
$k{=}5$ matrix expansion ($\approx{}12.8$\,k cycles per \texttt{gen\_matrix})
and 9-bit public-key packing ($\approx{}1.6$\,k cycles per
\texttt{polyvec\_compress\_pk}).

On \textsc{WEAVER-2048}, end-to-end performance is dominated by matrix sampling
and serialization; \texttt{gen\_matrix} costs $\approx{}17.4$\,k cycles per call
in the AVX2 build, and fused \texttt{polyvec\_basemul\_acc} accounts for
$\approx{}3.3$\,k cycles per dot product at $n{=}512$.
